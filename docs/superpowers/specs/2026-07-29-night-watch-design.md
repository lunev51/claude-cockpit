# Фаза 8 — «Ночная смена»: авто-продолжение после сброса 5-часового лимита

## Цель

Оставлять кокпиту работу на ночь, не боясь лимитов: когда 5-часовое окно
исчерпано и Claude встал посреди задачи, кокпит сам дожидается сброса окна
(точное время известно из `resets_at` OAuth-поллера) и отправляет «продолжай»
в ту же живую сессию. Утром — отчёт: во сколько встали, во сколько
продолжились, что пропущено и почему.

Решения пользователя (брейншторм 28.07): **глобальный тумблер** (не
по-вкладочно), продолжение — **всегда текст «продолжай»** (очередь Ctrl+Q
едет своим штатным Stop-механизмом после), выключение — **только вручную**.

## UX

- Кнопка **🌙** в панели действий (после ⌨), + действие палитры «Ночная
  смена: включить/выключить». Вооружённый режим виден издалека: кнопка горит
  акцентом (`--accent`), в дашборде (Ctrl+D) — секция «Ночная смена».
- Секция дашборда показывает: состояние (выкл / вооружена / ждёт сброса
  N вкладок к HH:MM), и журнал последнего взвода — построчно: «01:12 —
  вкладка cockpit встала по лимиту», «02:47 — окно сбросилось, продолжаю»,
  «02:47 — helper пропущена: ждёт ответа на диалог».
- Тосты в ключевые моменты: «встали по лимиту, продолжу в HH:MM»,
  «продолжил N вкладок», «недельный лимит — ждать нечего».
- Компенсаторы ручного выключения: «продолжай» НЕ отправляется во вкладку,
  которую пользователь сам трогал после остановки (перехватил — отменяем её
  продолжение), и никогда — в `waiting`/`dead`.

## Архитектура

**`src/main/night-watch.js`** — чистая фабрика `createNightWatch(deps)`, вся
логика в main (рядом с сессиями и поллером). Renderer только дёргает
тумблер и рисует состояние. Инжектируемые зависимости:

```js
createNightWatch({
  now,                        // () => ms
  setTimer, clearTimer,       // (fn, ms) => handle / (handle) — таймеры инжектируются, тесты без ожидания
  refreshUsage,               // () => Promise<snapshot> — немедленный опрос OAuth-поллера (его refresh())
  getTabStatus,               // (tabId) => 'working'|'waiting'|'done'|'stuck'|'dead'|null
  writeToTab,                 // (tabId, text) — текст+\r в pty вкладки (через manager.write)
  emit,                       // (event, payload) — 'night:changed' в renderer
  powerBlocker,               // { start(), stop() } — обёртка electron powerSaveBlocker ('prevent-app-suspension')
  journal,                    // { append(entry), readAll(), reset() } — файл в userData, атомарная запись
  config,                     // { fiveHourThreshold: 95, wakeMarginMs: 60000, staggerMs: 10000, maxResets: 4, retryMs: 300000, maxRetries: 3 }
})
```

Возвращает: `{ arm(), disarm(), isArmed(), onTabStop(tabId, prevStatus),
onUserInput(tabId), snapshot(), dispose() }`.

**Точки интеграции (существующий код):**
- `sessions.js` / `applyHookEvent`, ветка `Stop` (после гарда поколения):
  main прокидывает `nightWatch.onTabStop(tabId, prevStatus)`, где
  `prevStatus` — статус вкладки ДО применения Stop. Конкретно: обвязка в
  ipc.js уже подписана на `onEvent`-события sessions; она держит карту
  tabId → последний известный статус из `'tab:status'` и на Stop-событии
  зовёт `onTabStop` с предыдущим значением из карты. sessions.js о
  night-watch не знает и не меняется (кроме, при необходимости, эмита
  события Stop, если текущих событий недостаточно).
- `ipc.js` / `'term:write'` (единственный путь клавиатуры пользователя в
  pty): рядом с `manager.write` — `nightWatch.onUserInput(tabId)`.
- IPC: `night:toggle` (invoke → новое состояние), `night:get` (invoke →
  snapshot), событие `night:changed` (push в renderer).
- `config.js`: секция `nightWatch` с дефолтами выше.

## Жизненный цикл

1. **Взвод (`arm()`).** Флаг armed, журнал начинает новый «взвод»
   (`journal.reset()` + запись «armed»), счётчик обработанных сбросов = 0.
   Никаких таймеров заранее — ждём событий.
2. **Детект (`onTabStop`).** Условия: armed && `prevStatus === 'working'`.
   Тогда немедленный `refreshUsage()`:
   - `fiveHour.percent >= fiveHourThreshold` → это остановка по лимиту:
     вкладка в `pending` (`{tabId, detectedAt, resetsAt: fiveHour.resetsAt}`),
     запись в журнал, тост, планирование пробуждения.
   - `sevenDay.percent >= 99` при этом → недельный лимит: НЕ планируем,
     запись «weekly-limit» в журнал, тост. Вкладка не в pending.
   - Иначе — обычное завершение задачи, ничего не делаем.
   - `refreshUsage()` упал/данных нет (`ok:false`) → консервативно НЕ
     считаем лимитом (ложное «продолжай» хуже пропущенного), запись в журнал.
3. **Ожидание.** Один таймер на `max(resetsAt) + wakeMarginMs` (окно у всех
   вкладок общее). `resetsAt === null` → планировать нечем: запись в журнал,
   вкладка не в pending. Пока `pending.length > 0` && armed —
   `powerBlocker.start()`; опустело/disarm — `stop()`.
4. **Пробуждение.** Контрольный `refreshUsage()`:
   - `fiveHour.percent < fiveHourThreshold` → окно сбросилось. Для каждой
     pending-вкладки по порядку (стаггер `staggerMs`):
     - статус `waiting`/`dead`/вкладки нет → пропуск, запись причины;
     - был `onUserInput(tabId)` позже `detectedAt` → пропуск («перехвачена»);
     - иначе `writeToTab(tabId, 'продолжай')`, запись, счётчик++.
     После прохода: pending очищен, тост «продолжил N вкладок», блокер снят.
   - Всё ещё ≥ порога (часы разошлись, поллер отдал кэш) → перепланировать
     через `retryMs`, максимум `maxRetries` раз; исчерпали — запись в журнал,
     pending очищен, блокер снят.
5. **Потолок.** `maxResets` обработанных сбросов за один взвод; считается
   ПО СОБЫТИЯМ ПРОБУЖДЕНИЯ (одно пробуждение = один сброс, сколько бы
   вкладок оно ни продолжило), ночь физически вмещает 2–3. Достигли —
   режим остаётся armed, но новые детекты только журналируются
   («потолок исчерпан»), без планирования.
6. **Выключение (`disarm()`).** Таймер снят, pending очищен, блокер снят,
   запись «disarmed». Только вручную (решение пользователя).
7. **Рестарт приложения.** Armed-состояние НЕ переживает перезапуск
   (взведение — осознанное вечернее действие; авто-взвод после падения
   опаснее пользы). Журнал переживает — утренний отчёт доступен всегда.

## Обработка ошибок

- Никогда не бросать наружу: любой сбой (`refreshUsage` reject, битый
  журнал, отсутствие вкладки) — запись в журнал и деградация к бездействию.
- Битый файл журнала → начать пустой + `.bak` (тот же паттерн, что recipes).
- «Продолжай» уходит через `writeToTab` с тем же гардом непустого текста,
  что весь остальной вброс; проверка статуса — непосредственно ПЕРЕД
  записью, не при планировании.

## Тестирование

`test/night-watch.test.js`, `node --test`, все зависимости фейковые
(инжектированные таймеры дёргаются руками):
- детект: working+Stop+95% → pending+таймер; done+Stop → ничего; 50% → ничего;
- ложный детект: refreshUsage ok:false → ничего + журнал;
- недельный лимит → нет планирования + журнал;
- пробуждение: сброс подтверждён → «продолжай» в живую вкладку; waiting/dead/
  перехваченная → пропуск с причиной;
- ретраи: окно не сбросилось → retryMs × maxRetries → сдача;
- потолок maxResets; disarm посреди ожидания; блокер start/stop по инварианту
  «pending непуст && armed»;
- журнал: append/reset, битый файл → `.bak`.

Renderer-часть (кнопка, секция дашборда) — по конвенции проекта без
юнит-тестов, живая приёмка.

## Вне скоупа (осознанно)

- Отложенный старт задачи по времени («поставил в 23:00 — начни в 02:00») —
  тот же механизм таймеров, отдельная фича, если попросят.
- Авто-выключение режима (пользователь выбрал ручное).
- Продолжение после недельного лимита (до трёх суток ожидания — не ночной
  сценарий).

## Глобальные ограничения (как во всех фазах)

Никаких новых npm-зависимостей и нативных модулей; логика в чистых модулях
с инжекцией, тесты `node --test`; никогда не бросать наружу; в smoke не
спавнить процессы, не трогать userData и НЕ стартовать powerSaveBlocker;
только токены дизайна v2; комментарии по-русски; голый CR в pty запрещён —
любой вброс через существующие гарды.
