# Исследование: копирование в кокпите с макбука

**Глубина**: focused/wide · **Дата**: 10–11.08.2026 · **Статус**: ПРИЧИНА НАЙДЕНА И ВОСПРОИЗВЕДЕНА

## ДИАГНОЗ (11.08, доказан на чистом экземпляре кокпита)

Буфер обмена ни при чём. **На маке в терминале с работающим Claude Code
невозможно выделить текст мышью** — копировать просто нечего.

1. Claude Code включает отслеживание мыши: в потоке pty есть `CSI ?1000h`,
   `?1002h`, `?1003h`, `?1006h` (проверено чтением кольцевого буфера вкладки).
   Пока эти режимы включены, xterm.js отдаёт мышь приложению и своё выделение
   не строит.
2. Выделение при активной мыши возможно только «форсированное». Логика
   xterm.js: `isMac ? (altKey && macOptionClickForcesSelection) : shiftKey`.
   На Windows Shift+перетаскивание работает (проверено: выделение появилось,
   текст ушёл в системный буфер). **На macOS опция `macOptionClickForcesSelection`
   по умолчанию `false`, и кокпит её не включает — значит выделить нельзя ничем.**
3. Правый клик копирует одно слово, потому что xterm на macOS по умолчанию
   выделяет слово под курсором (`rightClickSelectsWord`), а обработчик кокпита
   копирует уже это слово. Отсюда жалоба «копируется только слово».
4. Cmd+C молчит по той же причине: `term.getSelection()` пуст, ветка выходит
   без копирования.

**Фикс СДЕЛАН** (ветка `fix/mac-selection`): xterm получает
`macOptionClickForcesSelection: true` в `initTerminal` (`terminal.js`), в
шпаргалку клавиш (`hotkeys.js`) добавлена строка про Option/Shift — иначе фичу
невозможно обнаружить.

Живая проверка на пробном экземпляре с подменой платформы на macOS
(`navigator.platform = MacIntel` через CDP — xterm определяет мак именно по
нему), в браузере по СЕТЕВОМУ адресу, в работающем TUI Claude Code:

| Условие | Обычная протяжка | Shift | Option |
|---|---|---|---|
| до фикса (опция false) | нет выделения | нет | **нет** — выделить нечем |
| после фикса | нет выделения | нет (так и задумано на маке) | **выделение есть, текст ушёл в системный буфер** |

Контрольный маркер в буфере: без опции остаётся нетронутым, с опцией —
перезаписывается выделенным текстом. На Windows Shift+протяжка работала и до
фикса (проверено там же).

Тест-страж `test/terminal-selection.test.js`; четыре мутации краснеют — опция
удалена, опция `false`, опция закомментирована, строка шпаргалки удалена. 1080
тестов зелёные.

Проверка на чистом экземпляре: в PowerShell-вкладке и на стартовом экране
claude (мышь ещё не перехвачена) выделение и копирование работают; в рабочем
TUI Claude Code обычное выделение не возникает вовсе, Shift+перетаскивание
возвращает и выделение, и копирование.

## Коротко (первый круг, до диагноза)

В Chromium по сетевому http-адресу (точная среда мака) **все три кокпитных пути
копирования работают** — проверено настоящими жестами мыши и клавиатуры, с
чтением системного буфера. Значит поломка либо специфична для браузера мака
(вероятнее всего Safari), либо человек упирается не в буфер обмена, а в то, что
выделить текст нечем: заглушка эстафеты перекрывает терминал целиком.

Отдельно найдены три реальных дефекта в самих путях копирования — они не
обязательно причина жалобы, но чинить их надо (см. «Находки»).

## Что проверено фактом (стенд, 10.08)

Стенд: свой http-сервер на порту 48311, страница с xterm.js той же версии,
скопированный один-в-один `copyText` из `src/renderer/js/clipboard.js`.
Открывался по СЕТЕВОМУ адресу `192.168.0.86:48311` (не localhost — тот
считается защищённым контекстом и проверка соврала бы). Браузер — Chromium 151.

| Проверка | Результат |
|---|---|
| Среда | `isSecureContext: false`, `navigator.clipboard`: **отсутствует** — среда мака воспроизведена |
| copyOnSelect (выделение мышью drag'ом) | **работает**: `execCommand`, в системном буфере оказался выделенный текст |
| Cmd+C кокпитным путём (перехват + execCommand) | **работает**: `execCommand`, буфер перезаписан выделением |
| Активация в момент копирования | `navigator.userActivation.isActive = true` в обоих случаях |
| Cmd+C БЕЗ кокпитного перехвата | на Windows ничего не копирует — там это не команда copy (ограничение стенда, не вывод) |
| Ctrl+C без перехвата | нативного события `copy` нет: xterm съедает Ctrl+C под `^C` |

Вывод: **кокпитный код в Chromium исправен**. Обвинять `execCommand` и
незащищённый контекст как таковые больше нельзя.

## Карта всех путей копирования

| Путь | Код | Как копирует | Жест в момент вызова |
|---|---|---|---|
| Выделение мышью (`copyOnSelect: true`) | `terminal.js:217` → `onSelectionChange` | `copyText` → `execCommand` | жеста нет, работает на «остаточной» активации от mousedown/mouseup |
| Cmd+C (мак) и Ctrl+Shift+C | `terminal.js:278` | `preventDefault` + `copyText` → `execCommand` | keydown |
| Правый клик по выделению | `terminal.js:225` | `copyText` → `execCommand` | contextmenu (полноценный жест) |
| Ссылка при заблокированном попапе | `api-boot.js:164` | `copyText`, результат проверяется тостом | клик |
| Голосовой ввод при занятой вкладке | `app.js:1314` | `navigator.clipboard.writeText` напрямую, по сети всегда падает в catch | — |

Штатный механизм самого xterm.js в этой карте отсутствует, хотя он есть:
`xterm.js` вешает обработчик `copy` на корневой элемент терминала и подставляет
выделение через `clipboardData.setData` (подтверждено в установленной сборке:
`addDisposableListener(this.element,"copy",…)` + `copyHandler`). Этот путь не
нуждается ни в Clipboard API, ни в `execCommand`, ни в защищённом контексте.
**Кокпит его глушит**: `ev.preventDefault()` на Cmd+C отменяет команду copy, и
браузер событие `copy` не порождает.

## Гипотезы, по убыванию правдоподобия

1. **Заглушка эстафеты перекрывает терминал.** `.handoff-curtain` —
   `position:absolute; inset:0; z-index:31`. Пока управление на ПК, мак не может
   ни выделить текст мышью, ни отправить Cmd+C в терминал (фокус паркуется на
   кнопке «Забрать управление», B4 от 10.08 усилил парковку). Снаружи это
   выглядит ровно как «копирование не работает». Проверяется мгновенно: видна ли
   заглушка, забиралось ли управление.
2. **Safari.** Все известные различия бьют именно сюда: Safari строже всех к
   тому, что считается пользовательской активацией, и известен тем, что не
   признаёт часть событий валидным жестом. `copyOnSelect` вызывает `execCommand`
   не из обработчика жеста, а из `onSelectionChange` — в Chromium спасает
   остаточная активация, в Safari может не спасти. `execCommand('copy')` в
   Safari 18 ещё жив, но помечен устаревшим.
3. **Копирование не из терминала.** Вне xterm в кокпите не копируется ничего:
   ни строки сайдбара, ни дашборд, ни поиск истории. Если человек выделял там —
   пути просто нет.
4. **Ctrl+Shift+C.** В Chrome это шорткат инспектора; до страницы может не
   дойти вовсе. На маке комбинация и не нужна, но в шпаргалке клавиш она
   заявлена как рабочая.

Регрессии в коде не видно: единственная правка после приёмки #30 — возврат
фокуса в `clipboard.js` (B2, #42), и она копирование не трогает, а чинит
соседнюю беду (раньше фокус падал на body, и следующий Cmd+C уже не доходил до
терминала).

## Находки, требующие починки независимо от причины

1. **Отказ копирования молчит.** `copyText` возвращает `true/false`, но в
   `terminal.js` результат не смотрит никто — ни тоста, ни строчки в консоли. В
   `api-boot.js` рядом сделано правильно (тост по результату, находка B3). То
   есть худший из возможных исходов — «нажал и ничего», без единого следа.
2. **Правый клик без выделения падает по http.** `terminal.js:231` зовёт
   `navigator.clipboard.readText()`, а по сети `navigator.clipboard` не
   существует: обращение к свойству `undefined` — синхронный TypeError, `.catch`
   его не ловит. Это ровно тот баг, который чинили в #30 для записи, только для
   чтения и оставшийся. Рядом, в ветке Ctrl+V, гард есть — здесь нет.
3. **Перехват Cmd+C отключает штатный механизм xterm.** См. выше. На маке
   разумнее не мешать браузеру: вернуть `true` без `preventDefault`, и xterm
   скопирует выделение сам, нативно.

## Что нужно с мака (один прогон, ~минута)

Стенд поднят и доступен из tailnet: **http://100.120.245.85:48311/**

На странице терминал с текстом, галочки «перехватывать Cmd+C как в кокпите» и
«copyOnSelect», кнопка-контроль и поле для вставки. Нужно: выделить строку
мышью, нажать Cmd+C, кликнуть правой кнопкой, нажать кнопку-контроль — и
вставить в поле внизу. Каждый шаг сам печатает в лог, что произошло: сработал
ли `execCommand`, была ли активация, возникло ли нативное событие copy.

Это даёт ответ по НАСТОЯЩЕМУ браузеру мака, чего Chromium на Windows дать не
может.

Остановить стенд: `Stop-Process -Name node` (или закрыть фоновую задачу
`b7xo7c7uz`).

## Предлагаемые фиксы (после подтверждения причины)

| Фикс | Что даёт | Риск |
|---|---|---|
| Не перехватывать Cmd+C: `return true` без `preventDefault` | нативный путь xterm, без `execCommand` и без Clipboard API | на Windows Ctrl+Shift+C остаётся как был; надо проверить, что xterm не отправит лишнего в pty |
| Тост при провале копирования | отказ перестаёт быть немым | лишний шум, если провалы часты |
| Гард на `navigator.clipboard` в правом клике | убирает молчаливый TypeError | нет |
| Копирование через WebSocket в буфер ПК | НЕ решает: текст нужен в буфере мака | — |
| HTTPS (Tailscale Serve) | снимает первопричину: Clipboard API станет доступен | план 4 отменён владельцем дважды |
